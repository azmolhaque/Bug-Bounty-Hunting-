# Exoscale — strategy after deep research, 2026-08-26

H1 closed as a clean negative: service-level IAM enforcement is sound across coverage, zones
and path normalisation. That result is **not** the end of the IAM story — it means we attacked
the *simplest* layer of a much richer authorization system, and the simple layer is the one
most likely to have been tested by the 45 researchers before us.

This document records what passive research established and re-ranks the hunt accordingly.
**No requests were made to Exoscale infrastructure to produce it** — sources are the public
`egoscale` SDK, published documentation and the program page.

---

## What the research changed

### 1. The authorization model is far larger than the portal shows

From `egoscale/v3/schemas.go`:

```go
type IAMRole struct {
    AssumeRolePolicy *IAMAssumeRolePolicy   // <-- NOT in the portal role form
    MaxSessionTtl    int64                  // <-- NOT in the portal role form
    Permissions      []string
    Policy           *IAMPolicy
    Editable         *bool
}

type IAMServicePolicyRule struct {
    Action     IAMServicePolicyRuleAction   // allow | deny
    Expression string                       // <-- CEL
    Resources  []string
}
```

Two things we had no idea existed when we designed H1:

- **`AssumeRolePolicy`** — a trust policy governing *who may assume the role*. The portal's
  role-creation form (which we walked through field by field) **does not expose it**. Whatever
  default a portal-created role receives is invisible to the person creating it.
- **`MaxSessionTtl`** — session lifetime for assumed credentials. Also absent from the form.

### 2. Role assumption issues real credentials

```
POST /v2/iam-role/{id}/assume     body: {"ttl": <int64>}
  -> {"key": ..., "secret": ..., "expires-at": ..., "role-id": ..., "org-id": ...}
```

It returns a **key and secret**. This is the exact primitive H1-PROCEDURE named as "the prize"
(*"a key intended to manage DNS can mint an unrestricted key"*) — via a route we never tested,
because the CLI and portal never showed it to us.

### 3. Policy rules are evaluated with CEL against a `parameters` map

Documented example:

```
parameters.bucket == 'my-bucket' && operation in ['list-objects', 'get-object']
```

So for rule-based policies, the decision is a **CEL expression over request-derived values**.
That is a fundamentally different attack surface from the boolean service toggles we spent
last session on, and it carries its own well-known failure modes.

### 4. Scope notes

- API v1 (CloudStack-compatible) was **deprecated 1 May 2024** and `api.exoscale.com/compute`
  is documented as no longer working. Worth **one** confirmation request, not a campaign.
- **Quota bypass became out of scope on 1 October 2025.** Do not hunt it.
- DBaaS runs in partnership with **Aiven**, who operate their own programme — treat DBaaS
  internals as belonging to someone else until confirmed otherwise.

## Re-ranked hypotheses

### H4 — role-assumption privilege escalation ⭐ START HERE

> **A least-privilege API key assumes a more privileged role and receives working credentials
> for it.**

Why this is the best test available to us:

| Criterion | H4 |
|---|---|
| Impact if true | **Critical** — org takeover from a dns-only key |
| Requests needed | ~6 |
| Cost | **0.00 CHF** — no billable resource |
| Customer risk | **None** — our own org's own roles |
| ID guessing | **None** — both role IDs are visible in our own portal |
| Prior coverage | Low. Not reachable from the portal UI or from ordinary CLI use |

Four sub-questions, in order:

- **(a) Which gate applies?** Is `POST /v2/iam-role/{id}/assume` denied by our `iam: deny`
  service policy, or governed only by the target role's `AssumeRolePolicy`? If the latter, the
  service policy is not the control — and the real control is one the portal never let us set.
- **(b) Can `zt-dns-only` assume `Owner`?** Owner role ID is visible in our own IAM page.
  Success returns Owner credentials → full organization compromise. **Critical.**
- **(c) Is `ttl` validated against `MaxSessionTtl`?** Request an absurd TTL (a year). If the
  server honours it, credentials outlive their intended lifetime — a real weakness even when
  the role assumed is not privileged.
- **(d) Do assumed credentials carry `Permissions`?** Specifically
  `reset-iam-organization-policy`, the named permission we deliberately left unchecked.

**Stop rule:** if (b) succeeds, capture evidence, **immediately let the session expire or
delete it, use it for nothing else, and write the report.** The escalation *is* the finding.

### H5 — CEL parameter-binding mismatch on SOS ⭐⭐ HIGHEST CEILING

> **A rule authorises an operation on bucket A while the storage layer performs it on bucket B.**

The policy decides using `parameters.bucket`. The S3 layer resolves the bucket from the
request. Two independent derivations of "which bucket is this?" is the classic setup, and S3
hands us the wedge for free: it has **two addressing modes**.

```
path-style:          https://sos-ch-gva-2.exo.io/BUCKET/key
virtual-host style:  https://BUCKET.sos-ch-gva-2.exo.io/key
```

If `parameters.bucket` is populated from one and the handler reads the other, a request can
satisfy a rule naming bucket A while operating on bucket B.

Test axes, all against **our own two buckets**:

| Axis | Probe |
|---|---|
| **Addressing mode** | policy names bucket A; access bucket B via the *other* mode |
| **Case** | policy `my-bucket`; request `My-Bucket` / `MY-BUCKET` (CEL `==` is case-sensitive; is the storage layer?) |
| **Host tricks** | trailing dot (`bucket.sos-ch-gva-2.exo.io.`), added port, uppercase host |
| **Missing parameter** | an operation where `parameters.bucket` is unset — does the CEL expression **error**, and does an evaluation error **fail open or closed**? |
| **Operation naming** | `put-object` vs multipart (`create-multipart-upload` + `upload-part`) — does a rule that denies one miss the other? |
| **Unicode** | NFC/NFKC-equivalent bucket names |

**The strongest single sub-test is the missing-parameter one.** Expression evaluators that
throw on an unbound field, wrapped in code that treats "no decision" as "no denial", are how
CEL-based authorization actually breaks in production.

### H6 — portal cross-tenant via the org slug

`portal.exoscale.com/u/<org-slug>/...` carries the organization in the path on **every page**,
and the slug is derived from the signup email (`gorib+exoA@intigriti.me` → `goribexoaintigritime`).
Every controller must re-check it; one that forgets fails quietly. Needs Org B. **Both slugs
must be ours — never construct or try another organisation's slug.**

### H3 — SOS ACLs (original plan)

Still worth running, but H5 subsumes its most interesting parts. Keep the anonymous-access and
presigned-URL checks.

### H2 — cross-org object IDs

Unchanged, still blocked on Org B, and now lower priority than H5/H6.

## Rules carried forward (unchanged, binding)

- `X-Intigriti-Username: gorib` on **every** request · **≤10 req/s**
- **Never** call `portal.exoscale.com/api/tickets`
- **No compute instances, ever.** Balance tripwire at 19 CHF. Delete what you create, same session.
- Only our own organisation(s). **No ID or slug is ever guessed** — every identifier used must
  be one we can see in our own portal (FO-14).
- A precondition is not a finding (FO-9). For H4 the finding is *working credentials for a role
  we should not hold*, not the endpoint existing. For H5 it is *bytes from bucket B returned
  under a policy naming only bucket A*, not a confusing error.
